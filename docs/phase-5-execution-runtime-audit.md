# Phase 5 execution runtime audit (before implementation)

## Existing lifecycle and execution scope

`AgentTree.run(Task)` deep-copies the Task, creates a `WorkflowState` with the Task ID, and calls the selected orchestration backend. The sequential backend invokes `OrchestrationContext.planning`, `delegation`, `execution`, `manager_review`, and `final_review` in order. The optional LangGraph backend invokes the same operations. Root planning and synthesis, Manager decomposition and review, Specialist execution, Manager revisions, and final review live in these operations and the existing engine; a second orchestration engine is unnecessary.

The run creates a `UsageCollector`, `ToolSession`, `ManagerCollaborationSession`, provider/model routing context, and an `OrchestrationContext`. Their mutable histories and budgets are execution-scoped in memory. `WorkflowState` holds phase results and trace snapshots; the last state and last collaboration messages are exposed after a run, but process exit loses them. `FinalResult` is returned synchronously. No background worker, store, durable checkpoint, or cancellation token exists. Manager work is sequential; Tool and collaboration timeouts use daemon workers. MCP clients, provider clients, callables, locks, threads, and context variables are live runtime objects.

## Serialization and safe boundaries

Task input, phase result dataclasses, trace events, usage summaries, Tool counters, and collaboration messages are data that can be encoded with an explicit allowlisted JSON codec after redaction and size checks. Provider instances, SDK clients, Tool and MCP implementations, callables, thread state, and credentials must never be serialized. A host must reconstruct the same Tree and its providers/Tools. A fingerprint of stable agent IDs, hierarchy, safe provider/model names, Tool IDs and assignments, collaboration policy, and relevant configuration can detect a changed definition. A fingerprint does not prove that a provider or Tool implementation is identical.

The safe replay boundaries in the existing design are **after a complete phase operation returns**: planning, delegation, execution, Manager review, and final review. A phase result includes completed Manager/Specialist/revision work and its trace. Root synthesis is currently inside final review, so the final phase checkpoint follows synthesis. Phase methods cannot safely resume halfway through their engine loops without additional operation journaling and finer-grained continuations. A completed phase must not be run again after recovery. The phase state machine and backend should call the same operations from the first unfinished phase.

## In-flight uncertainty and cancellation

Provider output is nondeterministic and can cost money when repeated. Tool calls and MCP calls may have external side effects; a crash between a side effect and its durable acknowledgment makes the outcome unknown. Replaying such a call is unsafe. Collaboration responses also consume provider and Tool budgets and must not be regenerated without a saved outcome. The runtime must write an in-flight operation marker before entering work that cannot safely be replayed and clear it only with a completed checkpoint. If recovery sees an in-flight marker without a complete phase checkpoint, it must block rather than invent completion or repeat the operation. This conservative policy preserves safety, though it limits mid-phase resumability.

Cancellation must be checked before and after each phase and within provider, Tool, collaboration, Specialist, and revision loops. A synchronous external call cannot be killed; its late result must be discarded and no subsequent phase may begin. The existing Tree object is guarded against simultaneous `run()` calls, so concurrent executions require separate reconstructed Tree instances. Background queue workers must be bounded, with store compare-and-swap transitions so cancellation and completion have one winner. SQLite is appropriate for local durability, while the store interface must admit a future PostgreSQL implementation. Runtime events and timestamps must be UTC and contain no raw exception text or credentials.
