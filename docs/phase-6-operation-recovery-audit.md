# Phase 6 operation recovery audit (before implementation)

## Phase 5 boundaries and limitation

`ExecutionRuntime` wraps the existing sequential or LangGraph backend and saves `WorkflowState`, usage, ToolSession and collaboration snapshots after planning, delegation, execution, Manager review, and final review. `AgentTree.run()` owns all runtime context variables. A durable SQLite `executions` row tracks state, fingerprint, version, owner, deadline and last checkpoint; the `checkpoints` row stores version 1 allowlisted JSON. A phase is marked `in_flight` before calling its existing method. Recovery after an unfinished phase currently blocks, even if several calls inside it already returned. The last completed phase checkpoint remains valid. SQLite version checks prevent stale record writes; no individual provider, Tool, or peer response has its own durable commit yet.

Inside planning, Root planning can invoke a provider and Tools before triage and manager discovery. Delegation iterates Managers and calls decomposition; a provider-backed Manager may use Tools and request another Manager, whose response may itself use Tools. Execution iterates Manager assignments and Specialist IDs; each Specialist provider can have several Tool rounds. Manager review iterates subtasks; a REVISE decision starts a bounded Specialist re-execution round and then another review. Final review may trigger more bounded revisions, followed by Root synthesis. A direct Root response ends during planning. The existing trace is cloned at phase boundaries; Tool and collaboration events are merged at completion. `ExecutionRuntime` keeps a small lifecycle event list in checkpoint/record JSON, but it has no independently queryable durable event sequence.

## Replay and identity choices

Pure orchestration aggregation can be recomputed from committed lower-level results. External provider calls may cost money and vary; completed responses should be reused, while an uncertain in-flight response may be retried with a new physical attempt and explicit uncertainty history. A Tool call may have external side effects. Existing FunctionTool/MCPTool contracts have no recovery declaration, so their default must be UNKNOWN and uncertain in-flight calls must block. A PURE Tool may be retried. An IDEMPOTENT Tool requires a stable idempotency identity honored by its implementation. A RECONCILABLE Tool may query its external system; UNKNOWN findings block. Neither a function name nor a provider brand establishes replay safety.

Logical keys can be derived from execution ID plus stable phase/Manager/Subtask/Specialist/revision/turn/call positions. Provider call inputs require a digest check on replay. Stable IDs for Manager messages are necessary when a response is committed before the enclosing decomposition result. A physical attempt ID and number should be separate from the logical key. A committed result must be durable before downstream work proceeds. A checkpoint remains a coarse state snapshot, while operation rows are authoritative for finer completed calls after it. An incomplete phase can be rerun only through journal-aware operation wrappers; this is not generic deterministic replay of arbitrary user code.

## Data and safety

The journal can store normalized `ProviderResponse`, `ToolResult`, Manager outcomes and internal phase operation results using the existing allowlisted JSON codec, bounded payload sizes, and redaction. It must not store provider objects, Tool callables, MCP clients, credentials, locks, or raw exception text. Existing cancellation checks in provider/Tool/collaboration loops and the watchdog remain; late results must not commit over CANCELLED. SQLite operation state and append-only event sequence should use transactions and optimistic versions. In-memory and SQLite stores need matching semantics. Recovery inspection should be read-only and give machine-readable block reasons. Process ownership still limits safe local recovery; multi-host leases are out of scope.

## External comparisons

- [Temporal activity guidance](https://github.com/temporalio/documentation/blob/main/docs/develop/python/best-practices/error-handling.mdx) describes at-least-once activity execution and stable idempotency keys. AgentTree adopts the distinction between logical identity and physical attempts; it does not adopt Temporal services or automatic Tool retries.
- [DBOS workflow steps](https://docs.dbos.dev/python/tutorials/workflow-tutorial) persist completed step outcomes and recover from the last completed step. AgentTree adopts durable reuse of completed operations while keeping its existing orchestrator and phase checkpoints.
- [OpenTelemetry event conventions](https://opentelemetry.io/docs/specs/semconv/general/events/) treat state changes and point-in-time outcomes as named events. AgentTree uses bounded ordered event envelopes around its existing `ExecutionEvent` contract, not a second tracing engine.
- [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests) bind a key to the first operation result and compare request parameters. AgentTree adopts input-digest validation and stable keys for declared idempotent Tools, without assuming every external service supports the same semantics.
