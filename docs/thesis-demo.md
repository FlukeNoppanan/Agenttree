# คู่มือเดโมวิทยานิพนธ์

เส้นทางหลักสำหรับการนำเสนอให้ผลแน่นอน ทำงานออฟไลน์ และต้องใช้เพียงแพ็กเกจ AgentTree พื้นฐาน โดยแสดงพฤติกรรมของเฟรมเวิร์กโดยไม่พึ่งความพร้อมของโมเดลหรือโครงสร้างพื้นฐานภายนอก

## ก่อนเริ่มเดโม

จาก root ของ repository:

```sh
.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
python -m pytest -q
python examples/thesis_demo.py
```

เส้นทางการนำเสนอเพิ่มเติมต้องติดตั้ง extras ที่เกี่ยวข้อง:

```sh
python -m pip install -e ".[langgraph,mcp]"
```

เปิด terminal ไว้ที่ root ของ repository เพิ่มขนาดตัวอักษร และรันคำสั่งหลักหนึ่งครั้งก่อนนำเสนอ ไม่ต้องใช้ข้อมูลรับรอง

## คำสั่งสำหรับเดโม

ลำดับชั้นหลัก:

```sh
python examples/thesis_demo.py
```

วงจรแก้ไขโดย Manager:

```sh
python examples/thesis_demo.py --revision
```

การประสานงานด้วย LangGraph ที่เทียบเท่ากันและเป็นตัวเลือก:

```sh
python examples/thesis_demo.py --backend langgraph
```

การเรียก MCP ภายในเครื่องผ่านชั้นเครื่องมือที่มีอยู่:

```sh
python examples/mcp_local_demo.py
```

คำสั่ง MCP จะเปิดเฉพาะ `tests/fixtures/mcp_test_server.py` เรียกเครื่องมือ `add` ที่ให้ผลแน่นอน แล้วปิด process โดยไม่ใช้บริการอินเทอร์เน็ต `examples/real_provider_template.py` เป็นเพียงเอกสารอ้างอิงการกำหนดค่าและไม่ควรใช้ในการนำเสนอแบบออฟไลน์

## ประเด็นที่ควรชี้ให้เห็น

1. นักพัฒนากำหนดเอเจนต์และนโยบาย ขณะที่แกนหลักชุดเดิมประสานงานทุกเฟส
2. ป้ายความสามารถใช้เลือก IT Manager และ Specialist สองตัวที่อยู่ภายใต้ Manager
3. Specialist ด้านเครือข่ายและ log มี provider binding ภายนอกแยกกัน
4. Manager ตรวจทานงานย่อยแต่ละรายการก่อน Root ตรวจทานขั้นสุดท้าย
5. โหมด revision แสดงการส่งต่อ feedback และการเรียก Specialist ทำงานซ้ำอย่างชัดเจน
6. `FinalResult` เป็นผลลัพธ์เพียงรายการเดียวที่ส่งให้ระบบเจ้าบ้าน
7. trace ที่เรียงลำดับทำให้ตรวจสอบแต่ละเฟสหลักได้
8. ตัวอย่างในขั้นที่ 20 นำเฟรมเวิร์กนี้กลับมาใช้กับสามโดเมนที่แตกต่างกัน

## แนวทางพูดประกอบ 3–5 นาที

- **ปัญหา:** ทีมพัฒนาแอปพลิเคชันต้องการการประสานระบบหลายเอเจนต์ที่นำกลับมาใช้ซ้ำได้ โดยไม่ฝังโดเมนหรือผู้ให้บริการโมเดลรายหนึ่งไว้ในแกนประสานงาน
- **แนวคิดของเฟรมเวิร์ก:** AgentTree แยกตัวตน การค้นหาความสามารถ provider/tool binding นโยบายลำดับงาน และสถานะการทำงานออกจากกัน
- **สถาปัตยกรรม:** แสดง Root -> Manager -> Specialist -> การตรวจทานโดย Manager -> การตรวจทานขั้นสุดท้ายโดย Root โดยมี registry และ trace รองรับลำดับงาน
- **งานสด:** รันคำสั่งเหตุการณ์จำลองและชี้ให้เห็น Task ที่ผ่าน normalization บริเวณด้านบนของผลลัพธ์
- **การกำหนดเส้นทางและการทำงาน:** ชี้ไปที่ Manager ที่เลือก Specialist สองตัว และตัวตน MockProvider สองรายการ ทั้งหมดใช้การเรียก `AgentTree.run(Task)` เพียงครั้งเดียว
- **การตรวจทาน:** แสดงการตัดสิน PASS ของ Manager และขั้นสุดท้าย หากมีเวลาให้รัน `--revision` และติดตาม REVISE -> feedback -> ประมวลผลซ้ำ -> PASS
- **ผลลัพธ์และ trace:** อธิบายว่าระบบเจ้าบ้านได้รับ `FinalResult`; ขั้นตอน trace แปดรายการที่แสดงเป็นบทสรุปของบันทึกเหตุการณ์ทั้งหมดตามลำดับ
- **การใช้ซ้ำและหลักฐาน:** อ้างถึง fixture ด้าน IT, HR และผลิตภัณฑ์ รวมถึงผลประเมินผ่านหกจากหกกรณี ระบุให้ชัดว่าสิ่งนี้แสดงคุณสมบัติซอฟต์แวร์ที่ผ่านการทดสอบ ไม่ใช่ความแม่นยำสากลของโมเดลหรือความสามารถในการปรับขนาดระดับ production

## แผนสำรองเมื่อเกิดความล้มเหลว

- **ไม่มี SDK เสริม:** ใช้เดโม sequential หลักซึ่งไม่มี dependency เสริม แล้วค่อยติดตั้ง extras ภายหลังแทนการแก้ปัญหาระหว่างนำเสนอ
- **provider จริงไม่พร้อมใช้งาน:** อย่าเปลี่ยนเดโมหลักไปใช้ provider จริง เพราะ `MockProvider` ให้ผลลัพธ์แน่นอนแบบเดียวกันได้ออฟไลน์
- **LangGraph ไม่พร้อมใช้งาน:** งด `--backend langgraph`; แบ็กเอนด์ sequential รันเฟสและ API สาธารณะชุดเดียวกัน
- **เดโม MCP ล้มเหลว:** แสดงหลักฐาน `FunctionTool` ที่ทดสอบไว้แล้วในตัวอย่างโดเมน IT หรืออธิบายเส้นทาง MCP จาก `docs/tools-and-mcp.md` เดโมหลักไม่ขึ้นกับ MCP

เดโมนี้ไม่ใช้ A2A, persistence, การประมวลผลแบบกระจาย, API สาธารณะแบบ async, การวางแผนเครื่องมืออัตโนมัติ, UI หรือบริการเครือข่ายภายนอก
