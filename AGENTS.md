# Repository Guidelines

## Project Structure & Module Organization

AgentTree is a Python 3.10+ package using a src layout. The developer SDK lives in `src/agenttree/framework.py` and its immutable configuration in `config.py`. Data contracts live in `src/agenttree/models/`, agent abstractions in `src/agenttree/agents/`, capability discovery in `src/agenttree/registry/`, vendor-neutral model interfaces in `src/agenttree/providers/`, explicit function/MCP tool contracts and execution in `src/agenttree/tools/`, triage/decomposition/execution/review/state services in `src/agenttree/core/`, stable event labels in `src/agenttree/tracing/`, and planning/delegation/execution/review/finalization coordination in `src/agenttree/orchestration/`. Low-level components must not import the SDK facade. Do not implement later steps until requested.

- `src/agenttree/` for the core, agents, models, registry, providers, tools, orchestration, and tracing packages.
- `tests/` for automated tests that mirror source modules.
- `examples/` for executable offline deterministic, provider-powered, and multi-domain SDK examples.
- `evaluation/` for reproducible offline scenario evidence and machine-readable results.
- `docs/` for architecture notes and development documentation.

Keep root-level files focused on repository configuration and contributor documentation. Create directories only when they have content.

Backend coordination lives in `src/agenttree/orchestration/backends/`. Keep optional LangGraph imports inside adapter construction; shared phase operations must remain independent of LangGraph and the SDK facade. Backend contract and equivalence tests live in `tests/test_backends.py`. Run real graph cases with the `langgraph` extra installed; graph fakes and import-blocking tests also work without it.

## Build, Test, and Development Commands

Create an environment with `python -m venv .venv` and activate it as described in `README.md`. Run `python -m pip install -e ".[dev]"` for editable installation with pytest. Run `python -m pytest` for tests and `python -m pip wheel . --no-deps --wheel-dir dist` to build a wheel. Package metadata and version live in `pyproject.toml`; keep runtime dependencies minimal.

## Coding Style & Naming Conventions

Follow PEP 8 with four-space indentation. Use `snake_case` for modules and functions, `PascalCase` for classes, and `UPPER_SNAKE_CASE` for constants. Prefer descriptive names, small modules, and typed public interfaces. No formatter or linter is configured yet. Keep abstractions domain-independent.

## Testing Guidelines

Real MCP transports remain optional under `agenttree.tools.mcp.transports`. Test their bridge/normalization contracts in `tests/test_mcp_transports.py`; with the `mcp` extra installed, the same file exercises local stdio and loopback HTTP using `tests/fixtures/mcp_test_server.py`. Keep the SDK imports lazy and transport details out of the loader, tools, executors, and orchestration.

Use pytest with `test_*.py` files and `test_*` functions. Tests are grouped by layer in `tests/test_models.py`, `tests/test_agents.py`, `tests/test_registry.py`, `tests/test_providers.py`, `tests/test_triage.py`, `tests/test_orchestration.py`, `tests/test_delegation.py`, `tests/test_execution.py`, `tests/test_review.py`, `tests/test_final_review.py`, `tests/test_state_and_trace.py`, `tests/test_tools.py`, and `tests/test_mcp.py`; no coverage threshold is set. Offline adapter contracts live in `tests/test_provider_adapters.py`; structured decision strategies and their full pipeline are covered by `tests/test_provider_decisions.py`; multi-domain evidence is covered by `tests/test_evaluation.py`. Add focused tests for new behavior and regression tests for bug fixes. Keep tests deterministic and isolate external services.

## Commit & Pull Request Guidelines

No Git history is available to establish existing conventions. Use short, imperative commit subjects, such as `Add initial project structure`. Keep changes focused. Pull requests should explain the purpose, summarize changes, link relevant issues, and report validation performed. Include screenshots for visible UI changes and disclose checks that could not run.

## Security & Configuration

Never commit credentials or local secrets. Provide placeholder configuration examples and ignore generated outputs and local environment files when introducing tooling.

### Step 7 - Orchestration Engine Foundation

- Implemented: dependency-injected `OrchestrationEngine`, immutable `OrchestrationPlan`, focused `OrchestrationStatus`, and stable `OrchestrationEventType` labels. The engine accepts a `Task`, runs triage, discovers matching managers, builds a plan containing manager ID snapshots, and records an `ExecutionTrace` without executing agents.
- Public API: `OrchestrationEngine.orchestrate(task) -> OrchestrationPlan`; injected `triage`, `registry`, and `manager_match_all` properties; `OrchestrationStatus.READY`/`NO_MANAGER`; and five event labels. All types are exported from `agenttree.orchestration`.
- Manager-selection policy: discovery passes triage capabilities to `CapabilityRegistry.find_by_capabilities()` with a `ManagerAgent` filter. ANY matching is the default; `manager_match_all=True` requires ALL capabilities. Registry iteration supplies deterministic order and one entry per registered manager, while the plan stores only IDs rather than mutable registry collections.
- No-match behavior and status design: missing managers, including an empty capability request, return a `NO_MANAGER` plan with no manager IDs and an explicit trace event. `READY` means managers are available for a future delegation step. A separate orchestration enum avoids misusing the task lifecycle; no `FAILED` state was added because dependency or contract errors currently propagate rather than being converted into plans.
- Trace integration: every plan records `orchestration.started`, `orchestration.triage_completed`, `orchestration.manager_discovery_completed`, and `orchestration.planning_completed` in order. No-match plans insert `orchestration.no_manager` before completion. Events contain task IDs and small immutable-value snapshots; traces remain observational.
- Dependency and mutation decisions: the host injects `BaseTaskTriage` and `CapabilityRegistry`; the engine constructs no globals or singletons. It validates task and triage-result identity, does not mutate the task or registry, and keeps lifecycle status in the plan. Managers and specialists are never called.

### Step 10 - Manager Review and Revision Foundation

- Implemented: abstract `BaseManagerReviewer`, deterministic `StaticManagerReviewer`, `RevisionRecord`, `SubtaskReviewOutcome`, `ManagerReviewResult`, aggregate `TaskManagerReviewResult`, and `ManagerReviewStatus` (`passed`, `partial`, `failed`, `revision_limit_reached`, `skipped`). Eight stable manager-review/revision event labels extend `OrchestrationEventType`; existing `ReviewDecision` remains the only decision enum.
- Public API: reviewers implement `review(task, subtask, manager, specialist_executions) -> ReviewResult`. `StaticManagerReviewer` accepts one PASS/REVISE/FAIL outcome or an ordered outcome sequence maintained independently per subtask. `OrchestrationEngine.review(execution, task, *, reviewer, executor, max_revisions=2) -> TaskManagerReviewResult` adds a separate phase without changing planning, delegation, or initial execution APIs.
- Decision semantics: PASS accepts the current round with no re-execution; FAIL terminates that subtask at manager review; REVISE preserves feedback and re-runs every specialist in the original assignment sequentially. Reviews receive only the complete execution set for their manager/subtask, including failed results, and manager/subtask ordering follows Step 9 execution and Step 8 delegation order.
- Revision counting: initial execution is revision zero. `max_revisions=N` permits exactly N re-execution rounds per subtask. Every completed re-execution increments `revision_count`; the new results are reviewed again. A further REVISE after N rounds produces `REVISION_LIMIT_REACHED`. With zero allowed revisions, the initial REVISE reaches the limit without re-execution.
- Feedback propagation: the engine creates a derived `Subtask` with the same stable ID and deep-copied metadata containing `revision.manager_id`, `revision.revision_number`, and `revision.feedback`. The unchanged executor API carries this data into the generic provider request. Original Task/Subtask metadata is never overwritten.
- Failure and aggregation behavior: revision calls reuse `BaseSpecialistExecutor`, so provider failures remain failed `AgentResult` values and can be reviewed again. Outcome objects retain initial and revision executions, every `ReviewResult`, and structured revision records. Uniform terminal outcomes propagate; mixed subtask or manager outcomes aggregate to `PARTIAL`, and empty review work is `SKIPPED`.
- Trace integration and immutability: review clones the Step 9 trace, then records manager review start/pass/fail/revision request, revision start/execution completion/limit, specialist revision execution, and manager completion events. Existing Task, Subtask, DelegationPlan, TaskExecutionResult, registries, agents, memberships, and traces remain unchanged.
